# ADR 062 — Public Records findability: client-side search index (not a chatbot)

Date: 2026-09-30
Status: proposed
Builds on: the wellfield-explorer pattern (`site/wellfield-explorer/data.js` —
data baked into a static JS file at build time, vendored `plotly.min.js`, zero
backend); the findings-feed pipeline (`findings_feed.py` / `gen_findings_feed.py`
/ `findings-feed.yml`); ADR 038 (`source_public` redaction column,
`check_publish_safety.py` gate). Does not touch and is not superseded by
`scripts/term_search.py` (a private dev-only PDF-text tool — different corpus,
different audience).

## Context

`site/public-records/` has grown to 2,264 documents across 46 chronological,
prev/next-only pages. There is no way to find "everything about PFAS" or
"everything about well AHW272R4" short of scrolling all 46 pages or using
`term_search.py`, which is a private CLI over raw PDF text, not user-facing.

The site is 100% static: GitHub Pages, no server, no secrets exposed to the
public, ever. `gen_findings_feed.py` already reads the public case-file Sheet
(`GSHEET_ID`) and renders it as static HTML via a pure function,
`findings_feed.build_pages()`, on a daily cron (`findings-feed.yml`) that
commits + redeploys (`pages.yml`). Every row already carries structured
fields: `date_filed`, `document_name`, `type`, `risks`, `severity`, `summary`,
`key_data_point`, `link`, `facility`, plus `source` for Hand-Curated rows
(already the redacted `source_public` column — see `parse_handcurated_rows`).

Two options were on the table: (A) a client-side search/filter UI, (B) an
AI/LLM chatbot over the corpus.

## Decision

**Build Option A.** Extend the existing pure renderer with a sibling function
that emits a compact JSON index of the same rows, generated by the same daily
job, served as a static file, searched entirely in the visitor's browser.

### Option A: client-side search index

| Dimension | Assessment |
|---|---|
| Complexity | Low — one new pure function + one new static file + vanilla JS |
| Build time | ~0.5–1 day for a working v1 |
| Runtime cost | $0/month, forever — static file, computed in-browser, no server |
| New infra | None — reuses `findings-feed.yml`'s existing daily commit/deploy |
| New secrets/attack surface | None |
| Accuracy risk | None — filters the exact rows already published; can't fabricate |

### Option B: AI/LLM chatbot

| Dimension | Assessment |
|---|---|
| Complexity | High — first backend this project has ever had |
| Build time | Weeks: hosting surface + secret mgmt + an embeddings/retrieval pipeline (2,264 summaries is too much to stuff in context every query) + rate-limiting + answer-governance design |
| Runtime cost | Nonzero, unbounded by default — pay-per-query against a public, unauthenticated endpoint |
| Accuracy risk | Real and specific to this project: free-text AI answers about regulatory readings have no per-answer refutation gate, unlike every hand-authored page on this site |

**Why A wins:** this site has a hard-won zero-server, zero-secret
architecture and a credibility model built on hand-reviewed static pages. A
chatbot is a categorically different risk class (unbounded public spend +
unreviewed public statements), not just a bigger build. Not rejected
forever — if ever revisited, scope it as retrieval-with-citations only
(translate a question into the same structured filters below, never
freeform number synthesis).

## Design

- **`findings_feed.build_search_index(rows) -> str`** — new pure function,
  JSON array, one object per row: `{date, title, facility, type, severity,
  source, excerpt, link}`. `risks` is deliberately omitted (same reason
  `render_entry` never shows it — internal case-file taxonomy, meaningless
  publicly). `excerpt` is `summary` truncated (~200 chars), falling back to
  `key_data_point` when `summary` is blank — full text stays on the HTML
  page a result links to via its existing `link`, so no new per-row
  addressability (anchors, page-N mapping) is needed anywhere.
- **Redaction must be computed here, not assumed from `rows`.** By the time
  a row reaches `render_entry`, `source` is already safe (`source_public`,
  never internal `source`/`note` — done upstream in `parse_handcurated_rows`),
  but `redact_names()` + `strip_embedded_date()` run *inside* `render_entry`
  itself and are never written back to the row. A naive index built by
  reading `row["document_name"]`/`row["summary"]`/`row["key_data_point"]`
  directly would therefore leak the un-redacted text. `build_search_index`
  must call the same `redact_names()`/`strip_embedded_date()` — ideally via
  one shared helper both `render_entry` and `build_search_index` call, so
  there is exactly one place redaction logic lives, not two that can drift.
- **Hand-curated classification mirrors the HTML exactly.** `render_entry`
  distinguishes hand-curated rows by `"source" in row` (auto rows have no
  `source` key at all). `build_search_index` preserves that: emit a
  `source` key (even `""`) only for hand-curated-origin rows. This gives
  `check_publish_safety.py` (Phase 2, below) the same free classification
  signal it already uses for HTML (`"Source:" in finding-meta`), no new
  heuristic needed.
- **`link` gets the same scheme check `render_entry` already does** — a
  Hand-Curated `drive_link` is human-typed free text, so only an
  `http(s)://`-prefixed value is kept; anything else becomes `""`. This
  check happens once, in the shared helper above, not duplicated.
- **`gen_findings_feed.py`** writes the index alongside the HTML in the
  same run — `site/public-records/search-index.json` — no new secret. Do
  **not** embed a generation timestamp in the file: `findings-feed.yml`'s
  diff-quiet guard (`git diff --cached --quiet -I'^<p>Generated...'`)
  exists precisely so a byte-identical dataset makes no commit; a
  timestamp in the JSON would need the same treatment or it reintroduces a
  daily no-op commit.
- **`check_publish_safety.py`** currently scans only `site/public-records/*.html`.
  It must also load and scan `search-index.json` — parse each entry's text
  fields, run the same `name_check.find_denylist_hits`/`find_heuristic_hits`,
  hard-block on a hand-curated entry (`"source" in entry`), warn-only on an
  auto entry — otherwise a name caught on the HTML could still ship in the
  index. **This gate extension ships in the same PR as the wiring that
  turns the index generation on** (Phase 2 below) — the index is never
  generated live without the gate covering it, no window where one exists
  without the other.
- **UI:** a search box + facet filters (Facility, Type, Severity, date
  range) above the existing paginated list on `site/public-records/`,
  reusing the `.finding` card CSS already in `style.css`. v1 does plain
  case-insensitive substring matching across title/facility/excerpt — no
  new JS dependency at this corpus size (~2,264 rows, a few hundred KB
  gzipped). Every field renders via `textContent` (or an explicit escape
  helper), never raw `innerHTML` interpolation — matches the Python side's
  blanket `_esc()` discipline even though the source is already curated.
  **Keep the existing chronological page-1…46 view as the default landing
  page** — it's what IndexNow currently pings Bing/AI-answer-engines about
  (`findings-feed.yml`'s IndexNow step targets `/public-records/`); search
  is an additional view/toggle, not a replacement.
- **Escalation path (not in this ADR):** if excerpt search proves too
  shallow later, a v2 could index full OCR'd PDF text the same way
  `term_search.py` already does, still 100% client-side (a bigger
  prebuilt index, bigger one-time CI build, still $0 runtime) — no need to
  reach for a chatbot even at that point.

## Build plan

Three overnight-coder items, staged in `documents/overnight-coder-queue.md`
(Lotext), each scoped to converge within the standard 3-round review cap
(`docs/overnight-coder.md` Step 7):

1. `coder:public-records-search-index` — the pure `build_search_index()` +
   shared redaction helper + tests. Not wired to anything live; ships on
   green tests like any pure-logic addition.
2. `coder:public-records-search-wire-and-gate` — wires generation into
   `gen_findings_feed.py` and extends `check_publish_safety.py` /
   `findings-feed.yml`'s `git add`, atomically. Live-path change,
   real-specimen verification mandatory (Step 3).
3. `coder:public-records-search-ui` — the client-side search/facet UI.
   Adds markup to the existing HTML template (`render_page` in
   `findings_feed.py`) plus new static JS/CSS files; no data-pipeline
   change (no new Sheet reads, no redaction logic, no gate change), no new
   privacy surface — it only ever displays what the Phase 2 gate already
   cleared.

## Consequences

- Ships inside the existing daily pipeline; no new workflow file, no new
  secret, no new deploy target.
- Public Records becomes browsable by facility/type/severity/date instead
  of scroll-only, with no new privacy exposure beyond what's already public
  in the HTML.
- A chatbot remains a possible future idea, explicitly not the next step.

## Alternatives considered

- **AI chatbot (Option B).** Rejected for now — see trade-off table above.
- **Full-text PDF search (client-side, v2 of Option A).** Deferred, not
  rejected — worth doing only if excerpt search proves too shallow in
  practice.

## Addendum 2026-11-02 — full-text search over the Mirror PDFs, plus a Year facet

Status: proposed (ships with `fulltext_search.enabled: false`; Trisha decides
before it goes live). Trisha, 2026-11-02: "we definitely need" full-text search
over the Mirror files, and a Year facet.

**Year facet (live with the next feed regeneration, no flag).** A Year dropdown
in the existing Filters panel, built from each entry's own `date` (the date on
the document, else the date filed: `findings_feed._search_entry`'s
precedence), newest first, plus "Not stated / other" when an entry has no date.
Its tooltip says which date it is.

**Full text (the escalation path this ADR named).** Still 100% static and $0:

- **Engine: Pagefind** (MIT, `pagefind[extended]` 1.6.0 in its own hashed
  `requirements-fulltext.txt`, used only by `fulltext-index.yml`). It writes a
  sharded index: the browser downloads only the shards a query needs, so the
  bundle can be large without every visitor paying for it. Built through its
  Python API (`add_custom_record`), so no per-document HTML pages are needed.
- **Pipeline:** `scripts/build_fulltext_cache.py` downloads each eligible
  document (Drive Mirror copy via the archiver's OAuth client, falling back to
  the public no-credential link; nSITE links via `nsite_client`), extracts its
  text with PyMuPDF and caches it, incrementally (at most
  `max_downloads_per_run` new documents a run, failures retried 3 times).
  `scripts/build_fulltext_index.py` joins the published `search-index.json`
  with that cache and writes the bundle. Both live in the Actions cache, never
  in git (data files are never committed). `pages.yml` restores the newest
  bundle into `site/public-records/fulltext/` at deploy time.
- **Scope = the gate** (check_publish_safety cannot read Pagefind's compressed
  shards, so the rules live in `fulltext_search.py` and are tested there):
  1. Only entries already in the PUBLISHED `search-index.json`: the existing
     redaction, gate and core-facility scope (ADR 064) carry over.
  2. Hand-curated rows are never full-text indexed (third-party material; the
     drive.file scope cannot read them anyway). They stay in title/summary search.
  3. Every document's text gets both of the feed's name redactions
     (`name_check.redact_denylist`, new, and `findings_feed.redact_names` /
     `REDACT_NAMES`), at cache time and again at index time.
  4. Per-document cap: the first 100,000 characters verbatim, then each
     remaining distinct word once (a 300-page WOI table stays findable by well
     ID). A bundle over `max_bundle_mb` (400) is refused, not deployed.
- **UI:** a "Search inside the documents' text (N of M documents so far)"
  checkbox appears only when `fulltext/coverage.json` exists. Results reuse the
  existing card, labelled "Matching text from the document" (not a summary),
  with matches highlighted. Pagefind's excerpt is rebuilt from text nodes and
  `<mark>` elements only, never parsed as markup.
- **Not covered:** scans with no text layer are only searchable once
  `backfill_mirror_ocr.py` / ADR 069 has given them one; image attachments
  and hand-curated files are not full-text searched.

**Open for Trisha before enabling:** the denylist redaction withholds the names
of EGLE and operator staff in public documents as well (it is the same list the
feed uses). Is that the right call for full text, or should official names stay
searchable?
